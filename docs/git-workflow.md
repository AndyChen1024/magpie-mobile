# Magpie Mobile Git 工作流与发布规范

本文为维护者待确认的设计稿。建议以 `main` 作为唯一长期分支，改动通过短分支和 PR 集成，正式版本通过标签定位。日常开发在 `main` 汇合，发布由维护者按平台确认。版本号均为流程示例。

## 分支与合并

| 分支 | 起点和去向 | 用途与示例 |
| --- | --- | --- |
| `main` | 默认分支 | 日常集成。保持可构建，作为常规发版的来源。 |
| `feat/*`、`fix/*`、`docs/*`、`chore/*` | 从最新 `origin/main` 创建，PR 合入 `main` | 分别用于功能、修复、文档和工程维护，例如 `feat/ios-usage-overview`。Agent 创建分支时使用 `codex/` 前缀，例如 `codex/feat/android-usage-overview`。 |
| `release/X.Y.x` | 从受影响的已发布标签创建，补丁 PR 合入此分支 | 只在已发布版本需要热修，且 `main` 上有这次补丁不应带入的改动时使用，例如 `release/1.2.x`。补丁发布且修复回流后即可清理。 |

1. 开工前先核对 `git status --short --branch`，更新远程分支信息，再从对应基线开分支。已有未提交改动时先确认归属。需要并行工作时可使用独立 worktree。
2. 单个 PR 聚焦一个可验收的改动，可按契约、Android、iOS 分批交付。每批都须保持已合入平台可用。依赖尚未合入的 PR 时，在描述中写明合并顺序。
3. PR 标题使用 `类型(范围): 简明描述`，例如 `fix(ios): retry usage after network recovery`。范围可用 `android`、`ios`、`shared` 或 `repo`。默认使用 Squash merge，合并提交沿用 PR 标题。分支无后续依赖时可在合并后清理。
4. 维护者检查最新差异、验收记录和适用检查后合并。单维护者阶段可以在 PR 留下自检记录。有第二位可参与评审的维护者后，将至少一位非作者批准设为必需。`main` 只接受 PR 合并，并保护其免于强推和删除。
5. 已合入的改动导致回归时，从 `main` 开分支提交 Revert PR，复核受影响流程。需修复已发布安装包时，走下文的补丁发布流程。

## PR 验收与 GitHub 门禁

PR 至少写清改动原因、用户操作及预期结果、受影响的平台、相关 Issue 或设计，以及最新提交的验证结果。每项验证记录命令或操作、环境、结果和待补项。界面改动附受影响平台的脱敏截图，跨页面流程可附短录屏。接口变更在同一 PR 更新相关[架构](architecture.md)或[功能契约](usage/README.md)，列出上游版本或提交、接口或字段，以及实际验证过的错误场景。

| 改动范围 | 合并前的最低验证 |
| --- | --- |
| 仅文档 | 检查渲染、链接和 `git diff --check`。 |
| Android | 用项目的 Gradle Wrapper 构建 Debug 并运行适用单元测试。涉及交互时，在模拟器或真机走一遍受影响流程。 |
| iOS | 用 `magpie-ios` Scheme 构建 iOS Simulator 版本并运行已有且适用的测试。涉及交互时，在模拟器或真机走一遍受影响流程。 |
| 两端、共享逻辑或主机契约 | 两端都执行适用的构建和验证，复用同一份验收场景。若改动涉及真实主机连接、权限或数据读取，按契约补双端真机联调，注明设备系统、主机版本及样例数据或真实主机。 [用量验收用例](usage/acceptance.md) |
| CI、签名或打包 | 验证受影响的工作流或打包路径。发布前另核对实际用于分发的安装包。 |

规范启用时，先在 GitHub 为 `main` 开启 PR 合并要求及强推、删除保护。CI 接入前，维护者按表核对本地证据。规定的验证失败或缺失时，PR 保持待合并。Android 和 iOS 检查在 PR 与 `main` 上稳定运行后，再设为必需。若按路径跳过平台任务，必需的汇总检查仍须在每个 PR 上报告结果，以免文档改动卡在等待状态。合并前更新代码时，以本次待合并改动的检查为准。 [GitHub 必需检查说明](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks)

普通 PR 构建和测试使用无签名或模拟器环境。签名证书、商店凭据和发布写权限仅供授权的发布流程访问。按[仓库工作约定](../AGENTS.md)，Agent 执行远程推送、合并、推送标签或公开发布前须得到用户授权。

## 版本与发布

- **版本标识。** 正式标签用 `vX.Y.Z`，在整个仓库内唯一。`0.Y.Z` 阶段用 `Y` 表示功能、`Z` 表示修复，在发布说明中写明兼容性变化。从 `1.0.0` 起，`X` 用于不兼容变化，`Y` 用于向后兼容的功能，`Z` 用于向后兼容的修复。双端同批发布时使用同一个标签和用户可见版本号，对应 Android `versionName` 和 iOS `MARKETING_VERSION`。每个平台分别维护递增的上传构建编号，对应 Android `versionCode` 和 iOS `CURRENT_PROJECT_VERSION`。单端补丁在发布记录标明发布平台和另一端当前的发布状态，下一次联合发布再统一版本号。
- **选定候选提交。** 通过 PR 把本次发布平台的版本号和构建编号写入配置，从 `main` 中选定一个已通过适用检查的提交 SHA。记录该 SHA、平台、构建编号与目标渠道，用该提交的候选包验证安装、启动及受影响的核心流程。若产品用到了真实主机，记录经过验证的 Magpie 版本。
- **标记与分发。** 维护者批准后在通过验收的同一 SHA 上创建带注释的正式标签，按授权发布到相应渠道。优先使用已验收的候选包。若重新打包，复核实际分发包的版本、构建编号、签名和启动。发布记录包含标签、SHA、平台、构建编号、用户能感知的改动、已知限制和渠道状态。Android 和 iOS 的提交、审核和实际上线分别登记。
- **发布后修复。** 已公开标签保持固定。需要交付代码修复时，发布新补丁版本并递增构建编号，必要时先暂停仍在进行的分发。记录故障范围与修复所对应的标签。

### 已发布版本热修

如果 `main` 上的改动都可随补丁发布，按常规 `fix/*` PR 合入 `main` 后发补丁。如果补丁只能包含旧版与修复，就从受影响平台当前发布的标签（例如 `v1.2.0`）创建 `release/1.2.x`，再从该分支开 `fix/*`，通过 PR 合回维护分支。对维护分支的候选提交执行与常规发版相同的验收。选择高于该平台当前发布版本且仓库尚未使用的补丁版本，例如 `v1.2.1`。如果 `main` 尚缺修复，将修复提交 cherry-pick 到从 `main` 新建的分支，通过 PR 回流，并注明原补丁 PR 与发版标签。
